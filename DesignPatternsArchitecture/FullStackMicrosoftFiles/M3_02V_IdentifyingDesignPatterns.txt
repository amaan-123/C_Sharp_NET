Imagine working on a complex project where you constantly face the same challenges. Over time, you develop smart, repeatable solutions that make your work easier and more efficient. In software development, we call these repeatable solutions design patterns. They are tried and tested ways to structure your code, making it more efficient and scalable. In this video, you will learn to recognize and describe common design patterns. Design patterns are like reusable solutions for common problems in software design. They give you a standard way to tackle architectural challenges, making your code more reliable and easier to maintain. There are many design patterns that developers use to design their software. We'll explore a few of the most common. First, let's discuss Singleton Pattern, which ensures that a class has only one instance throughout your application and provides a single point of access to that instance from anywhere in your code. Developers use the Singleton Pattern to manage shared resources. For example, a database class can implement the Singleton Pattern to ensure there is only one connection to the database throughout the application. To implement this in C Sharp, a developer creates a public class called Database. They create a private variable that holds the instance of the database object and a private constructor that writes database connection established to the console when it's called. The developer then creates a public method called GetInstance that assigns the private variable to a new instance of the database object and returns that instance to the code that called it. But before it assigns the object to the private variable, it checks first to see if it's already populated. If it is, it uses the instance that already exists. This enforces the pattern that there is always only one instance of the database object in the program. The access modifier of the database constructor is private, which prevents any external class from creating a new instance of the database object. This is key to enforcing the Singleton Pattern. Now that we've explored the Singleton Pattern's role in managing a single instance across an application, let's look at another essential pattern, the Factory Pattern. This pattern not only helps in creating objects, but also ensures that your code remains stable and adaptable even as changes are made. Let's investigate how this Factory Pattern works. In the Factory Pattern, instead of creating an object directly, your code has a special method or class called a Factory to handle the creation for you. This way, your code doesn't need to worry about the details. The Factory takes care of it, making your program more flexible and easier to manage. The Factory receives some input, such as a parameter, that tells it what kind of object it needs. The Factory then decides which specific type of object to create based on that input. By using the Factory to create objects, the pattern keeps the code that requests an object separate from the code that actually makes it. This separation makes it easier to change or add new types of objects later on without affecting the code that uses them. To implement the Factory Pattern in C Sharp for a notification system, you start by creating a public interface called inotification. This interface will include a method called send which takes a message as a parameter. Then you move on to the next step, creating two derived classes that inherit from the inotification interface. One derived class will handle email notifications and the other will manage SMS notifications. Each of these derived classes implements the send method which outputs the notification to the console. Finally, the developer creates a new class called NotificationFactory that handles creating the email notification and SMS notification objects. They implement a method called createNotification that uses the inotification interface as its type. This method also takes an input parameter called channel that tells the Factory which type of notification object to create. Using this pattern, the developer can modify how the email and SMS notification objects are designed without impacting the code that requests them. The code that requires these objects just calls the createNotification method, passing in the channel parameter, and the Factory handles the rest. Finally, let's explore the Observer Pattern, a key behavioral pattern that is crucial for managing communication between objects in complex systems. Imagine you're developing a user interface that needs to update in real-time whenever the underlying data changes. This is where the Observer Pattern shines. It enables your system to respond dynamically to changes, keeping everything in sync without manual intervention. The Observer Pattern enables one object to automatically notify and update multiple other objects when its state changes. This pattern is particularly useful in systems where different parts must respond to changes, such as updating a user interface when data changes. Let's learn how a developer might implement this pattern in C Sharp for a weather station application. To implement the Observer Pattern, you start with creating a public interface called iObserver. This interface includes a single method named update, which accepts a temperature parameter. This step lays the foundation for how observers will receive updates. The next step is to create the WeatherStation class, which acts as the subject. This class manages a list of iObserver instances and is responsible for notifying all registered observers whenever there is a change in its internal state, like a temperature update. It has a private list member called Observers that can hold iObserver interface objects. It also has a private member called Temperature that holds temperature values. The developer creates methods for adding and removing objects from the Observers list as well as a method called NotifyObserver, which iterates through each object in the Observers list and then calls the update method on each one from the Observer interface. This method passes the values set in the temperature member to the update method. The temperature member is set in the final method in this class called SetTemperature. This method includes an input parameter called NewTemperature and the method sets the private temperature member variable to its value. It then calls the NotifyObserver method. The developer then creates a concrete, public-derived class called PhoneDisplay. The class will notify a phone interface of any changes in the temperature. The developer can use an app or a tool built into the phone to listen for this message. The developer also creates a concrete, public-derived class called DesktopDisplay to update any desktop apps or tools of the change in temperature. Each class is a derived class of the iObserver interface and implements the update method from that interface. The update method passes the temperature as a parameter and writes the temperature to the console in a message. To use the observer in the program, the developer creates new instances of WeatherStation, PhoneDisplay, and DesktopDisplay objects. Then they call the RegisterObserver method on the WeatherStation object to register a new observer for each object. They pass in the PhoneDisplay and DesktopDisplay objects as parameters when they call this method. Now to update each display, they simply call the SetTemperature method on the WeatherStation object, passing in a new temperature. The iObserver interface, along with the Subject class, will update all displays with a new temperature. These patterns are ways that developers can simplify code and make it easier to maintain. Design patterns provide developers with blueprints for creating well-formed, readable, and extensible code. In this video, you learned how to recognize and describe key design patterns like Singleton, Factory, and Observer. These patterns are essential tools that help you write code that's efficient, easy to maintain, and built to last.
